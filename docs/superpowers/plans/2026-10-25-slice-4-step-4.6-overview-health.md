# Slice 4 Step 4.6 — Overview (P1) + System Health (P7) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the Overview and Health placeholders in the dashboard SPA with the real P1 and P7 pages, including a prominent red banner when scans fail (naming Anthropic credit exhaustion when the stored error says so).

**Architecture:** Frontend-only. The 4.2/4.3 endpoints already exist and are live; the pages read them through typed TanStack Query hooks (60 s poll, except CloudWatch metrics which load once per page view). All "what is wrong" logic lives in one pure module (`lib/problems.ts`) so the banner, the badges and the tests share a single definition.

**Tech Stack:** React 19, TypeScript 6 (strict), Tailwind 3, TanStack Query 5, react-router 7, Vitest + Testing Library (already in `dashboard-ui/`).

**Spec:** `docs/superpowers/specs/2026-10-18-serverless-dashboard-design.md` §4.2 P1 / P7, §3.4 (error mapping), §10 row 4.6 (SPEC §4 Slice 4 row 4.6). Response shapes: `src/dashboard/api/schemas.py`.

## Global Constraints

- Read-only, signal-only: no write calls, no new backend endpoints. Backend Python is not modified in this step.
- Polling stays at the client default (`refetchInterval: 60_000`, no background polling, `staleTime: 30_000`); `GET /api/system/metrics` must NOT poll (design §4.2 "P7 metrics cadence"): `refetchInterval: false`, `staleTime: 300_000`.
- 503 `db_resuming` is handled by the existing retry policy (`shouldRetry`/`retryDelay` in `api/queries.ts`); pages show a "waking the database" state, never the red failure banner, while it retries.
- The Overview must be readable on a phone (design §4.4 anti-goal): single column below `md`, no horizontal page scroll.
- Colour is never the only signal: every badge carries a text label. Contrast follows the existing `StatusChip` palette (≥ 4.5:1, light and dark).
- All text from the API (scan errors, alarm reasons, reasoning) is rendered as React text, never as HTML, and long strings are truncated with the full text in `title`.
- Existing conventions: Tailwind utility classes, `dark:` variants, `*.test.ts(x)` beside the file, `vi.stubGlobal("fetch", …)` for API tests (see `App.test.tsx`), `npm run lint` with `--max-warnings 0`.
- No links to `/signals/:id` yet (route lands in Step 4.7); signal rows are plain text.

## Review Focus

1. Cold Aurora (503 `db_resuming`) — expect "Waking the database…" on the pages, no red banner, recovers on its own.
2. `health.alarms === null` (CloudWatch unavailable/denied) — expect an amber "alarm status unavailable" badge with the note, never a green badge.
3. A window with `scan: null` — expect neutral "not run yet" before its fire time, amber "missed" once `fire_time + 15 min` has passed, never green/red.
4. Scan `error` text that is very long, multi-line or contains `<script>` — expect truncated plain text, no layout break, no HTML injection.
5. Credit detection false positives/negatives — expect the credit wording only when the stored error contains "credit balance" (case-insensitive); any other FAILED scan gets the generic failed-scans wording.

### Task 2: Pure problem-detection and formatting logic

**Files:**
- Create: `dashboard-ui/src/lib/problems.ts`, `dashboard-ui/src/lib/format.ts`
- Test: `dashboard-ui/src/lib/problems.test.ts`, `dashboard-ui/src/lib/format.test.ts`

**Interfaces:**
- Consumes: `OverviewResponse`, `WindowSummary`, `AlarmState` from Task 1.
- Produces:
  - `type Tone = "ok" | "bad" | "warn" | "neutral"`
  - `isCreditError(text: string | null | undefined): boolean` — true iff text matches `/credit balance/i`.
  - `interface Problem { id: "credits" | "scans_failed" | "alarm" | "forecaster" | "alarms_unavailable"; tone: "bad" | "warn"; title: string; detail: string }`
  - `collectProblems(o: OverviewResponse): Problem[]` — ordered most severe first.
  - `windowState(w: WindowSummary, now: Date): "ok" | "failed" | "running" | "pending" | "missed"`
  - `format.ts`: `formatR(r: number | null): string` (`+1.25 R`, `−0.40 R`, `—` for null), `formatDuration(seconds: number | null): string` (`850 ms` is not needed; seconds → `42 s` / `3 m 05 s`; null → `—`), `formatCountdown(seconds: number): string` (`2 h 05 m`, `4 m 10 s`, `now` at ≤ 0), `truncate(text: string, max: number): string` (adds `…`), `formatAge(seconds: number | null): string`.

Rules for `collectProblems` (these are the spec for the red banner):
1. `credits` (bad): any `health.last_scan.error` or any `windows_today[].scan.error` satisfies `isCreditError`. Title `Anthropic credit balance too low`, detail `Scans are failing at the LLM call; top up credits.` plus the number of affected windows.
2. `scans_failed` (bad): at least one window/last scan has `status === "FAILED"` and the failure is NOT a credit error (if rule 1 fired it already covers those windows). Title `N scan window(s) failed today`.
3. `alarm` (bad): any `health.alarms` entry with `state === "ALARM"`; detail lists display names.
4. `forecaster` (warn): `forecaster.stale > 0` or `forecaster.errors_last_window > 0`.
5. `alarms_unavailable` (warn): `health.alarms === null`; detail is `health.alarms_note`.
A healthy overview returns `[]`.
